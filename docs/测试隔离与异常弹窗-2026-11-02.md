# Windows 测试隔离与异常弹窗处理

日期：2026-11-02。

## 事实与定位范围

用户在 23:20:53 的截图中看到 `SystemResourceNotifyWindow: dotnet.exe` 原生访问错误。团队本轮临时 `StateProbe.dll` WPF 宿主在 23:19–23:20 确有连续初始化失败：资源程序集重复赋值、SQLite provider 未初始化、图标 pack 资源缺失、编码 provider 未注册。它使用默认 shell 桌面和屏幕外坐标，没有创建独立 Win32 Desktop。

该时间重合，临时宿主存在确定的测试基础设施错误；但没有取得截图对应的原生调用栈或当次 WER dump，不能据此声称已经确定底层访问错误的唯一模块原因。查询时没有活动的 `dotnet.exe`、`ComicVerse.exe` 或 `WerFault.exe`，未批量终止其他项目进程。发现的旧 dotnet dump 日期为 10 月 17 日，不作为本次故障证据。

正式 v1.3.0 EXE 在该轮诊断期间没有被替换。临时 WPF 宿主已停用，其异常不能归类为产品缺陷，也不能作最终验收证据。

## 改进

- 构建和真实 App 自检统一通过 `tools/Invoke-IsolatedProcess.ps1` 创建新的 Win32 Desktop，明确指定子进程桌面；没有 `SwitchDesktop` 或全局输入操作。创建失败拒绝退回用户默认桌面。[Microsoft CreateDesktopW 文档](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-createdesktopw)
- 子进程归入本次 Job，超时或启动器退出会终止该子进程树；日志记录 PID、实际退出码、超时、桌面和工作目录，不凭窗口消失认定成功。
- 进程错误模式只作用于本次进程树，不修改注册表或系统级设置。CLI 实测显示 CLR 宿主启动后可能重设部分继承标志，因此实际 App 的 `--smoke` 在静态初始化和 OnStartup 内重新设置本进程模式，并记录当前线程真实桌面和标志。[Microsoft SetErrorMode 文档](https://learn.microsoft.com/en-us/windows/win32/api/errhandlingapi/nf-errhandlingapi-seterrormode)
- 自检 Dispatcher 未处理异常落到 `smoke-crash.txt`，以失败码退出；交互式程序仍保留正常错误提示。禁止把故障吞掉后继续报告通过。
- 自检中发现未观察 Task 异常也记录故障并以失败码退出，不能只记日志后返回成功。
- 统一使用项目实际 App 的自检入口。禁止新建临时 WPF 宿主反复修宿主初始化错误。

## 启动器自身验证

在普通沙箱以不含 WPF 的 PowerShell 子进程验证：

- 子进程通过 Win32 API 读取的桌面名为 `ComicVerse-QA-*`，确实是新桌面，而非屏幕外坐标。
- 进程内重新设置后错误模式为 32771（0x8003）；设置不涉及系统级状态。
- 有意返回 7，启动器记录真实 ExitCode=7、TimedOut=false，不能认定通过。
- 30 秒等待任务限制为 2 秒，记录 ExitCode=124、TimedOut=true，并清理本次 Job。

证据位于 `artifacts/launcher-verification/`。这两项仅验证测试基础设施，不代表产品逻辑回归通过。新增产品修复仍须冻结最终候选后独立 QA 完整验收。

实际 App 后续验证：`--smoke --verify-failure-exit` 和 `--smoke --verify-task-failure-exit` 各注入一次预期测试异常，均在独立桌面记录实际 ErrorMode=32771、生成故障文件并退出1，未超时。这是自检故障处理验证，不能计为正常产品回归通过；相应证据分别在 `app-failure/`、`task-failure/`。
